## 1. What shipped

`v0.4.0` is two halves of one rule: a `Strong` validator issued by the origin,
and nothing weaker, may be reused after the reader that captured it is gone.
The first half decides what a consumer may learn about an asset's identity; the
second writes blocks to a disk a later process reads back.

**Identity exposure.** `ArResolver::GetAssetInfo` publishes four neutral values
in `ArAssetInfo::resolverInfo` — `resolvedIdentifier`, `size`,
`validationToken`, and `stability` — under the names the first consumer's own
contract uses ([RESOLVER.md](../architecture/RESOLVER.md) §3). The token is the
backend's captured validator: opaque here and opaque all the way out, never
parsed as an `ETag`, compared for recency, or read as a time.
`ArAssetInfo::version` carries the token only for a `Stable` identity, because
that field travels with no stability beside it and a consumer that finds a token
there treats it as fit to key durable reuse on. The dictionary publishes a weak
token anyway, beside the `stability` that qualifies it: a weak validator that
*changed* is still evidence the asset changed, and it is proof of sameness that
weak cannot supply.

Identity is answered from the open this process already performed rather than
from a new request, which is both cheaper and more correct — the identity a
consumer needs is the identity of the bytes it holds, not of whatever is
published now. Once two opens of one identifier have captured two different
validators, `Stable` degrades to `Unstable` and `version` goes empty for the
rest of the process.

**Persistence.** `usdasset::cache::DiskBlockStore` implements
[CACHE.md](../architecture/CACHE.md) §8. Blocks fetched for a `Stable` identity
are written into a directory the host names, and a process that starts cold
reads them instead of the network. The admission test is the validator's
strength *and its author*: an entity tag is the origin's and means the same
thing to whoever reads the entry next, while a `Derived` identity —
`usdAssetLocal`'s device, file index, size, and mtime — is strong only for as
long as that backend holds the file open, and does not cross a process
boundary. A `Weak` or absent identity is never read for, and its write is
refused inside the store rather than outside it, so `rejected` counts what the
rule turned away.

Entries are keyed by the whole `CacheKey`; the identity is written inside the
entry and compared byte for byte, so a name collision costs a miss and can never
serve one asset's bytes for another's. Publication is by rename into the
destination's own directory, filenames are sixteen hexadecimal characters, and
header and body carry separate checksums. The directory may be deleted at any
moment, under a live reader, at a cost of time.

The release also adds:

- **two environment variables**, `USD_HTTP_RESOLVER_PERSISTENT_CACHE_DIR` and
  `USD_HTTP_RESOLVER_PERSISTENT_CACHE_BUDGET`
  ([CONFIGURATION.md](../reference/CONFIGURATION.md) §3). Naming a directory is
  the only switch and there is no default location;
- **`persistedHits` and `persistedWrites`** in
  [METRICS.md](../architecture/METRICS.md) §2.2, as block counts rather than
  byte counts — the bytes are already in `bytesFromCache`, and a second counter
  for the same bytes would be double counted by anything summing the section;
- **`boundary_persisted_local`**, a fourth row in the shared boundary suite: the
  same row definition as `cached-local` with the tier underneath it, so the two
  are a comparison rather than two experiments;
- **`usdAssetCache_persistence`** and **`httpResolver_identity`**, which ask what
  the suites cannot: whether a weak validator ever reaches the disk, whether an
  entry from revision A can serve a read of revision B, what a scribbled file
  costs, what the directory a hostile URL was hashed into actually contains, and
  the publication rules as a table; and
- **a sixth baseline scenario and a cross-process case**. `httpResolver_stage`
  re-invokes its own executable with the cache directory in its environment and
  counts the fixture server's log, so "a second process pays nothing" is
  measured against a second process rather than simulated inside one.

## 2. What explicitly did not ship

No asynchronous read API and no prefetcher. The disk tier is not a shared cache
between concurrent processes: it is safe for them to share a directory, because
publication is atomic and an entry carries its own identity, but nothing
coordinates their fetches — single-flight remains within a process. There is no
default cache location and no way to admit a weak validator to disk.

`GetAssetInfo` is the whole identity surface. No resolver context, no asset
mutation, and no write path ships in this release.

No binary package ships. This remains a source-tag release; packaged artifacts
are planned for `v0.6.0`.

## 3. Capability delta against `v0.3.0`

- **Identity:** `GetAssetInfo` publishes four neutral values; `version` carries
  a token only for a `Stable` identity; a contradicted identifier withdraws
  reusability for the rest of the process.
- **Persistence:** blocks for an origin-issued `Strong` identity outlive the
  process, under a swept directory budget.
- **Configuration:** two persistent-cache variables, opt-in by directory.
- **Observability:** `persistedHits` and `persistedWrites`.
- **Verification:** a fourth boundary row with the tier underneath it, a
  persistence test module, an offline identity table, ten socket-backed stage
  cases, and a baseline scenario measured across two processes.

Revision binding is unchanged. A reader that observes a changed validator fails
subsequent reads, and a persisted entry from another revision is a different
cache identity rather than a hit.

## 4. Recorded I/O baseline

Fixture: the 128 MiB synthetic asset from
[BASELINE.md](../reference/BASELINE.md), served by the loopback fixture server
with a strong `ETag`. Every byte is derived from its offset and every scenario
verifies the bytes it counted. The reopened row additionally uses a persistent
cache directory that the run created and deleted. Measured on Windows AMD64,
MSVC 19.34.31937.0, Release, with the shipped transport and cache defaults.

| Scenario | uncached requests | cached requests | uncached bytes | cached bytes | Result |
| --- | ---: | ---: | ---: | ---: | --- |
| metadata-only open | 1 | 1 | 0 | 0 | Unchanged, deliberately: the `HEAD` is how the identity the cache is keyed on gets revalidated |
| header and index read | 18 | 3 | 69632 | 131072 | Unchanged from `v0.3.0` |
| bounded spatial query | 19 | 18 | 331776 | 1507328 | Unchanged from `v0.3.0` |
| bounded query, reopened | 19 | 1 | 331776 | 0 | New. A second open moves no bytes; the one request is the metadata `HEAD`, which is supposed to still happen |
| full sequential read | 33 | 33 | 134217728 | 134217728 | Identical, and still asserted identical rather than close |
| parallel readers | 152 | 26 | 2654208 | 1507328 | The cached row lands at 25 or 26 depending on which reader wins each claim; the harness asserts it is below the uncached row rather than equal to a constant |

The new row is the release's claim, and it is a pair rather than a number: the
same bounded query costs 19 requests and 331776 bytes on a first open and 1
request and 0 bytes on a second. `persistedWrites` is 0 on the reopened cached
row because the writing was done by the warm-up reader, whose numbers are the
cached bounded-query row's.

No row regressed against `v0.3.0`. The full sequential read is unchanged, which
is what keeps the cache from disguising a whole-asset download as an
optimization, and the metadata-only open is unchanged because revalidation is
the thing that makes reuse safe. The complete tables, including cache counters
and latency quantiles, are in [BASELINE.md](../reference/BASELINE.md).

The row this baseline still cannot record is a `Weak` or `Unavailable` identity
failing to reuse anything: the fixture server serves one asset with one strong
`ETag`, and the harness measures bytes rather than policy. That rule is tested
where a test can vary the validator — `usdAssetCache_persistence` opens one
identifier under a strong, a weak, and an absent validator and asserts that only
the first writes an entry and only the first reads one back.

library, which the module links when it detects one; no other platform
requirement changes.

## 8. Known limitations

- Persistence requires a `Strong` validator **issued by the origin**. A
  backend-derived strong identity — which is what `usdAssetLocal` produces — is
  in-memory only, so the persistent tier does nothing for local assets outside
  the boundary row that relabels the kind on purpose.
- There is no default cache directory. A deployment that names none gets no
  persistence, and that is the shipped default.
- The directory budget is enforced by a periodic sweep, not per write, and
  evicts oldest-written first rather than least-recently-used: refreshing a
  timestamp on every hit would turn a read of a cached block into a write. The
  directory can therefore exceed its budget between sweeps, and the budget is
  raised when the host's number cannot hold a few of the largest entry written.
- The tier is not a cross-process coordinator. Two processes may share a
  directory safely, but they do not share single-flight, and both may fetch the
  same missing block.
- Asset info is keyed by asset path while this resolver hands out one reader per
  open, so two `ArAsset`s over one URL may be two revisions. Once contradicted,
  an identifier's `stability` stays `Unstable` for the rest of the process; it
  never returns to `Stable`.
- `GetModificationTimestamp` returns an invalid timestamp by design. This costs
  a `SdfLayer::Reload` a request and never costs a wrong answer.
- The HTTP backend's known limitations from [`v0.2.0`](v0.2.0.md) and the cache
  limitations from [`v0.3.0`](v0.3.0.md) are unchanged, except that cache state
  is no longer necessarily memory-only.

## 9. Migration notes

There is no source-level migration for existing `AssetReader` clients, and no
diagnostic code is added, removed, or redefined.

Resolver users gain two optional environment variables. Both are inert until
`USD_HTTP_RESOLVER_PERSISTENT_CACHE_DIR` names a directory, so an unchanged
deployment behaves exactly as it did at `v0.3.0`. A deployment that does name one
should expect the directory to grow to its budget, to be safe to delete at any
time, and to contain nothing reversible to a URL.

Consumers reading `ArAssetInfo` see populated fields where they previously saw
empty ones. The compatibility rule is the one in
[RESOLVER.md](../architecture/RESOLVER.md) §3: `validationToken` is opaque, and
`stability` is the field to act on. A consumer that keys durable reuse on
`ArAssetInfo::version` gets a token only when that is safe, and an empty field
otherwise — which is the case it must already handle.
